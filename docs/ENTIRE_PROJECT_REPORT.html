In one minute

CAMS lets patients book clinic appointments online. Doctors see their day and mark who came. Admins run the whole clinic. On top of that sits a research side: a model trained on public data estimates how likely each booking is to be a no-show, and a simulation tests whether using that estimate to double-book some slots would help a clinic.

Three rules shaped every decision.

  • One slot, one patient. The same doctor, date and time can never be booked twice. The database enforces this, so it holds even when two people click at the same moment.
  • The app never overbooks. Overbooking is studied only in the simulation. In the app, staff just see a Low, Medium or High badge that is advisory. Nobody is refused a slot because of it.
  • Every number comes from a script. Results are written to files by code and checked by another script, so nothing in this report was typed from memory.

Status. The web app, the model, the simulation and the checks are all finished. The recorded test run has 784 tests: 778 passed, 0 failed and 6 were skipped on purpose. No real patient data is used anywhere. The app is filled with made-up people.

The problem we picked

A clinic books patients into fixed time slots. Some of them never turn up. That empty slot is wasted doctor time, and another patient could have used it.

Many clinics respond by overbooking: they put two patients in some slots and hope one of them stays away. When that works, the doctor stays busy. When both come, everyone waits and the doctor works late.

So we asked two questions. Can a computer tell which bookings are risky? And if it can, does using that to choose which slots to double-book actually beat simpler rules? The booking website is the real product. The model and the simulation are how we answered the questions.

No real clinic data was available to us. The model learned from public datasets, the app runs on synthetic records, and everything the simulation assumes about a clinic is stated. The project shows a method and its trade-offs. It does not claim clinical results.

The three parts

Web app

What patients, doctors and admins actually use. Written in Flask with a MySQL database.

Prediction model

Reads six facts about a booking and returns a chance that the patient will not come.

Simulation

Runs thousands of pretend clinic mornings under different double-booking rules and measures waiting and overtime.

The web app

Who can do what

RoleWhat they can do
PatientRegister and log in. Browse doctors and free slots. Book, cancel and reschedule. Join a standby list for a day that is full. Change their own password.
DoctorSee their own schedule with patient names and the advisory badge. Create slots. Close and reopen free slots for leave. See who is on standby. Cancel an appointment. Mark past appointments completed or no-show.
AdminAdd doctors and generate their slots. Close and reopen any doctor's free slots. See and cancel any booking. Mark outcomes. View the risk flag status and the Models and simulation page.

A typical day

  1. An admin adds a doctor and generates slots, for example 20-minute slots from 09:00 to 13:00 on weekdays.
  2. A patient registers, opens the doctor's page and books a free time. The booking appears under My appointments.
  3. The doctor opens My schedule. Each booking carries a Low, Medium or High badge marked "advisory only". Patients never see it.
  4. After the appointment time starts, the doctor marks the booking completed or no-show. These outcomes become the history the model learns from.

Features added beyond the basics

Leave
A doctor can close free slots for a date range. Closed slots disappear for patients. Closing never cancels an existing appointment, and reopening only touches closed slots.
Standby list
If a day is full, a patient can ask to be told when something frees up. Standby reserves nothing and gives no priority. When a slot is free again the patient sees a notice and books it the normal way, first come first served.
No overlapping appointments
A patient cannot hold two appointments whose times overlap, even with different doctors.
Models and simulation page
An admin page that shows the model card, the three risk bands and the simulation figures, all read from the saved result files.
Phone-friendly look
A Swiss-minimal design: one blue accent, plain type, generous spacing. Tables turn into labelled cards on a phone-width screen.

Safety built in

  • Passwords are hashed, never stored as typed.
  • Every form carries a CSRF token, and every route checks the user's role.
  • A patient who asks for another patient's booking gets a 404, as if it did not exist.
  • Five wrong passwords for one email from one place pause further tries for fifteen minutes.
  • Ids and dates in URLs are range-checked. A test sends junk to every route as every role and expects no server errors.
  • All database access goes through SQLAlchemy with bound parameters.

Under the hood: 30 routes in six blueprints (main, auth, account, patient, doctor, admin), 16 page templates, a services.py that holds all booking rules, and a read-only queries.py for pages.

The rule that matters most

Imagine two patients open the same doctor's page, both see 09:20 free, and both press Book within the same instant. A program that first checks "is it free?" and then saves can let both through, because each check happens before either save.

CAMS does not check first. It just tries to save, and the database decides who wins.

How the database guarantees it

  • The slots table has a unique key on doctor, date and time, so a slot exists once.
  • The bookings table has a hidden generated column. It copies the slot id while a booking is alive and becomes empty when the booking is cancelled. That column must be unique, so two live bookings cannot share a slot, and a cancelled booking frees it. A completed or no-show appointment keeps its slot.
  • Rescheduling inserts the new booking and cancels the old one in a single transaction. If the new slot is taken, everything is undone.
  • Closing a slot for leave uses the same mechanism: a closed row held in the doctor's own name. A patient booking and a doctor closing the same slot are decided like two patients.

How we proved it

Three tests were written before the code and shown failing first: two simultaneous requests for one slot give exactly one success, six simultaneous requests across 25 slots give one winner per slot, and a direct SQL insert of a second live booking is refused. They run on SQLite and on real MySQL, because the project's database is MySQL.

The data

Learning needs examples of past appointments and whether the patient came. We used three public datasets, each for one job.

DatasetUsed forWhat it holds
Kaggle "Medical Appointment No Shows"Training the model and reporting results110,527 appointments from Vitória, Brazil, April to June 2016. No doctor id and no consultation times.
OpenML "Medical-Appointment"Checking that findings hold on a second dataset61,214 appointments from early 2017, with specialty, booking channel and hour. Its origin is not stated.
Hangu open dataConsultation lengths in the simulation only6,637 consultations from 381 half-day sessions of one physician at a private clinic in China.

Care we took

  • Target coding. The two datasets label attendance in opposite ways. In all our code the value 1 always means a no-show, and a test confirms both loaders agree on the same hand-made rows.
  • Cleaning is logged. The Kaggle file lost 16 rows to cleaning rules (fractional patient ids, impossible ages, appointments dated before they were booked). Each rule's count is written to a log file.
  • History uses only what was known. A patient's "earlier no-show rate" counts only appointments dated before the current booking date, so the model never peeks at the future.
  • Raw datasets are never committed. They live in a git-ignored folder, and the download steps are in data/README.md. The app itself never reads them.

The prediction model

The model answers one question for a booking: how likely is this patient to be a no-show? It is deliberately limited to six facts a real clinic could collect at booking time.

InputMeaning
ageAge in years on the appointment date
is_femaleSex, coded 1 for female and 0 for male
lead_daysDays between booking and the appointment
appt_weekdayDay of the week, Monday is 0
prev_appointmentsEarlier appointments whose outcome was already known
prev_no_show_rateShare of those earlier appointments that were no-shows

The same function, deployable_features(), computes these inputs during training and inside the app. A test pushes one booking through both paths and expects identical numbers, so the model sees the same thing in use as it did in training.

The ladder of models

We climbed in steps, so each step had to earn its place: an "always show up" baseline, a rule based on earlier no-show rate, logistic regression, random forest and gradient boosting. The score used is AUC-ROC. It runs from 0.5, a coin flip, to 1.0, a perfect ranking. Accuracy is never the headline, because always guessing "will show" is already right 0.815 of the time on the holdout while telling us nothing.

The honest reading: the model ranks patients usefully but not sharply. The deployable model with six inputs scores 0.727 (95% interval 0.719 to 0.735), only 0.005 below the research model with every feature. Random forest and gradient boosting are statistically close, and both beat logistic regression.

Guarding against fooling ourselves

  • The test set is the latest 20% of appointment dates, locked first and scored once per final model.
  • Tuning uses patient-grouped cross-validation, so no patient appears on both sides of a split. A test checks that 0 patients do.
  • An AUC above about 0.85 would be treated as a leak. Ours are well below. A model trained on shuffled labels scores 0.506, which is what chance looks like.
  • Class weights and resampling were compared. Class weights distort the probabilities and resampling made things worse, so the final model uses neither.
  • Calibration was tested. Neither Platt scaling nor isotonic regression improved the Brier score, so the model is left uncalibrated.
  • The SMS reminder shows a link with fewer no-shows, but reminders were sent selectively. We describe it as an association and never as a cause.

From a probability to a badge

Staff see three bands, set from the model card at 0.19 and 0.38 and chosen on training data so the holdout stayed a fair test. These are the real no-show rates on the holdout. The clinic-wide average there is 18.5%.

Even High bookings still attend more often than not. That is why the badge is advisory: a prompt for staff, such as a reminder call, and never a reason to refuse or move anyone.

The model uses age and sex. That raises fairness questions, so it is listed under limits. Removing both lowers AUC-ROC by only 0.011 in the feature test.

The simulation

We cannot run overbooking experiments on real patients, so we built a pretend clinic. One doctor works one half-day session of 240 minutes with 16 slots of 15 minutes. Patients arrive on time and are seen in slot order. A no-show uses no doctor time. Consultation lengths follow a lognormal curve fitted to the Hangu data, and each patient's chance of showing up comes from the saved model, applied to profiles drawn from the Kaggle holdout.

Every setting was run 1,000 times with fixed seeds, and differences are paired and reported with 95% intervals.

The policies compared

  • P0, no overbooking. One patient per slot.
  • P1, uniform. Every k-th slot gets a second patient.
  • P2, risk threshold. A second patient goes into slots whose first patient has a high predicted risk.
  • P3, learned. A small reinforcement-learning policy (REINFORCE) that sees the same risk plus its own earlier choices.

Every extra patient served costs waiting and overtime, and no policy wins on every column. For that reason we publish the full table and never merge it into one score, because any score would hide a choice about how much a minute of waiting is worth.

The headline question: does prediction add anything?

More double-booking always serves more patients, so comparing policies that double-book different amounts proves nothing. The fair test double-books exactly the same number of slots and only changes which slots. This is experiment S6.

  • Choosing by predicted risk lowered the mean wait compared with evenly spaced extras in most settings. At the 0.3 threshold the difference is −0.412 minutes (95% interval −0.678 to −0.145). Against random choice the gain is larger.
  • The share of double-booked slots where both patients came, the outcome overbooking tries to avoid, was 50.7% with the risk threshold. It was 63.2% with evenly spaced slots, 63.3% with random slots and 26.8% for an oracle that knows who will not come.
  • The oracle does far better, so the model captures only a small part of what perfect knowledge would give.

Plain summary. Prediction adds a modest benefit over spacing extras evenly, and a clearer one over picking at random. Because the simulation uses the model's own risk as the truth, this is also the best case for the model.

What happens when assumptions are wrong

  • Risk estimates off (S3). Overestimating risk by 0.10 raises the double-booked slots at the 0.3 threshold from 4.36 to 8.94 and the mean wait from 11.0 to 24.8 minutes. Overestimating hurts more than underestimating helps.
  • Different clinic no-show rate (S4). A fixed risk threshold adapts on its own, while a "every k-th slot" rule has to be retuned for each clinic.
  • More variable consultations (S5). Holding the mean at 13.4 minutes, the more the lengths vary, the more overbooking costs in waiting.

A learned policy (S7)

To learn, the policy needs one number to maximise, and there is no single right price for delay. We fixed three stated settings and trained one policy for each. The reward is patients served, minus a cost for patient-hours waited, minus a cost for doctor overtime hours. Training, validation and evaluation use separate random seeds.

The learned policy beats the best hand-made rule only under the moderate setting. Under light costs it ties, and under heavy costs both almost never double-book. This is a small, honest result and not a claim that reinforcement learning wins.

On Vercel

The app runs as one Python function and needs a hosted MySQL 8 database, because the no-double-booking rule relies on MySQL's unique generated column. Set three environment variables on Vercel: DATABASE_URL, SECRET_KEY and CLINIC_TIMEZONE (for example Asia/Kolkata, since Vercel's servers run on UTC). Prepare the hosted database once from a laptop, then deploy. The full steps are under "Deploy to Vercel" in README.md.

The deployment setup was checked by a clean install of only the web app's requirements and a walk through each role on that stripped-down copy. An actual Vercel deployment has not been run from this repository yet.

What it cannot do

  • No real clinic data. The model learned from a Brazilian public clinic, the consultation times come from a private clinic in China, and the app runs on made-up records.
  • Assumed clinic behaviour. One doctor, one half-day, equal slots, patients on time, seen in order. In the simulation the model's risk is the true risk, so S6 shows the most prediction could help.
  • Short data. Kaggle covers about six weeks, so seasons are not captured, and its holdout is only 5 dates.
  • Modest accuracy. AUC-ROC 0.727, and even a High flag is wrong more often than right. It is a nudge, not a decision.
  • Findings transfer only partly between the two datasets, so a clinic would need its own data.
  • Age and sex are inputs. That is a fairness concern. Because the flag only informs staff and the slot rule never changes, nobody is denied a slot on that basis.
  • The login throttle is per process. On Vercel it slows guessing rather than stopping it.
  • A preprint is cited. The reinforcement-learning idea follows Amalina and An (2026), an arXiv preprint that has not been peer reviewed.

Glossary

No-show
A booked patient who does not turn up and does not cancel.
Overbooking
Giving two patients the same slot, hoping one of them will not come.
AUC-ROC
How well a model ranks risky cases above safe ones. 0.5 is a coin flip, 1.0 is perfect.
Holdout
Data kept aside, here the latest appointments, and scored only at the end so the result is a fair test.
Leakage
When a model accidentally sees information from the future or from the answer, giving scores that look great and mean nothing.
Calibration
Whether a predicted 30% really happens about 30% of the time.
Brier score
A measure of how far predicted probabilities are from what happened. Lower is better.
Unique key
A database rule that refuses a second row with the same value, used here so one slot holds one live booking.
Generated column
A column whose value the database computes from other columns. Ours copies the slot id for live bookings and is empty for cancelled ones.
CSRF token
A secret in each form that stops another website from submitting actions as a logged-in user.
Discrete-event simulation
A simulation that jumps from one event to the next, such as a patient arriving or a consultation ending. SimPy does this.
REINFORCE
A simple reinforcement-learning method: try decisions, see how well sessions went, and nudge the policy toward the choices that did better.
Oracle
A pretend policy that knows in advance who will not come. It shows the upper limit of what prediction could give.
Advisory
Shown to staff for information only. It never changes who can book.
